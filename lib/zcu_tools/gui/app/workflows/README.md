# gui/app/workflows — Workflow run and form ownership

**Last updated:** 2026-10-09，Resume capture Stop 與 producer delivery

WorkflowController stays fixed for its Window's lifetime. Each Start supplies EnginePorts and a pending TunablesHost. One private run state concentrates the binding, native acceptance, token, producer phase and retained Runner settlement. Replacement waits for terminal cleanup. Native Engine status and artifacts remain authoritative; the operation token is only a receipt.

TunablesHost owns one run's unique FormState, fixed evaluation capture and submitted expression input before native acceptance. Attaching Engine does not replace draft or base. Pending Apply rejects before draft writes. Controller.apply_tunables is the common GUI/RPC submission entry. Target and pending checks precede draft writes. Host submits complete ordinary values; Engine owns numeric validation, revision, step capture and journal publication. Invalid form input retains draft. Only successful publication accepts input/base. No holder enforcement or GUI revision guard is introduced.

Pause retains the original operation, local RUN lease, progress and run inputs after owner delivery. Resume calls Runner.continue_operation with the same token and settlement, without another begin or init. Stop during Resume capture retains ownership until continuation delivery without restarting the stopped native run. Terminal delivery settles the native outcome and releases admission/resources before notifying the view; view errors are logged without changing native outcome. Controller retains the original native control error across producer delivery or Resume admission unwind. Native failed reason takes priority over delivery errors. Idle paused failure finishes immediately; producing and resuming phases retain ownership until delivery or admission unwind. SessionDevices borrows shared public drivers. Hardware setup and limits remain with their existing owners.

Concrete T1WorkflowWindow and T1TuningPanel stay in zcu_lab. Window supplies per-Start resources and the fixed capture. Tuning presents the Controller-owned Host directly. RPC uses the same Window controls and shared transport. Start accepts optional leaf batches against current captured defaults; tunables edits submit the current shared draft, not Start defaults. Start and Resume call DeviceService's synchronous live capture of every connected driver through get_device_info. A named read failure rejects capture without cached fallback. Successful reads refresh session cache and return detached native models. Cached capture retains its separate public semantics.

Cross-lane integration requires acceptance. Records/PNG RPC, independent app composition, MCP, reload and CP remain incomplete. Offline evidence does not authorize hardware use or establish full F5/P2 acceptance.
