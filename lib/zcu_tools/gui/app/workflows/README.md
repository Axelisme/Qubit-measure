# gui/app/workflows — Workflow form submission

**Last updated:** 2026-10-09，pending／accepted run 的唯一 form binding

TunablesHost owns one run's unique FormState, fixed evaluation capture and submitted expression input before native acceptance. It attaches the accepted Engine once without replacing draft or base. Pending Apply rejects before any draft write. GUI and external edits submit complete current ordinary values through the same FormState/Engine seam. External edits use the same parsed GUI draft, without a GUI revision conflict guard. Engine owns numeric validation, revision, step capture and journal publication. Controller binding checks and whole-run cleanup are separate from this form binding; pending Host acceptance alone does not implement them.

Control identity will reject non-holder writes after it lands. This transition does not check holder and does not introduce a workflows-specific holder mechanism.

WorkflowController owns pending Start admission, worker startup/execute and cooperative Stop through OperationRunner. The worker holds the run lease until owner terminal delivery. SessionDevices borrows the shared device service's public drivers; native setup and driver limits remain with their existing owners. Concrete T1WorkflowWindow and T1TuningPanel attachments stay in zcu_lab and use the same captured inputs. Pause/Resume uses the same native run across operation segments. The controller borrows the shared ProgressService and keeps one Start-token factory across segments. Pause releases only the returned segment lease; Resume reacquires the lease before owner-thread cached-device capture. Completion, Stop and failure discard run progress. The concrete T1 attachment supplies app-owned status/Pause/Resume/Stop RPC via the shared remote dispatch and the same Window controls. It does not duplicate target checks, native status, capture or transport policy. The same concrete Window accepts optional plan/tunables leaf-path batches for RPC Start. It builds current captured defaults and delegates one batch to FormState, without changing a GUI draft on invalid input. Successful submission resets both panel bases to the submitted input. Native tokens remain pending receipts, not worker acceptance. No generic form overlay or new synchronization mechanism is introduced. The Controller exposes require_run_id for commands that must reject stale targets before touching draft. Concrete workflow.tunables edits use the accepted run's existing tuning panel with an app-owned agent actor. Empty batches submit current complete parsed input, not Start defaults. FormErrors retains invalid draft; only successful publication accepts input/base and clears local text. Paused Apply followed by Resume keeps prior records and reruns the uncommitted step with the latest native revision. Records/PNG RPC, independent app startup, MCP and source reload remain unimplemented. Offline Start/Stop evidence does not establish full F5/P2, CP or hardware acceptance.
