# Agent 自行做 UI e2e：元件驅動情境

## 結論

GUI 的行為驗證由 agent 自己完成，使用者走查只判斷外觀與操作手感。Agent 用元件驅動的情境驗證 UI：

- 操作只經使用者碰得到的元件，送真實的鍵盤與滑鼠事件。Disabled 元件點了沒有反應，和手動操作一樣。
- 判定只讀使用者看得到的狀態：底部文字、元件是否可按、tooltip、開啟的對話框、圖例。
- 每一步截圖，agent 自己看圖判斷畫面是否交代清楚。

情境分兩層：

- 框架行為的情境用合成 adapter，寫進 `tests/`。
- 實驗定義（例如 mux）的走查腳本不寫成 pytest，放在 task 的 scratch，用同一個 driver 在送 review-done 前跑完。原因是測試必須在刪掉 `zcu_lab/` 後仍然通過。

流程規則：有 UI 改動的票，驗收必須包含元件驅動情境。直接呼叫 Controller 或 MainWindow 方法的 smoke 不算 UI 驗證，review 要標出。

## 問題

mux GUI 的走查中，使用者在 Active tones 輸入 `[0,0]` 後，Run 變成 disabled，畫面沒有任何說明。使用者原話：「Run被屏蔽，然後什麼都沒發生」。

擋 Run 的原因只寫在 disabled Run 按鈕的 tooltip。底部的 Run 診斷只在按鈕的 clicked 路徑顯示，disabled 按鈕走不到。

Agent 事前跑過的 smoke 直接呼叫 `MainWindow.run_or_stop_tab`，繞過了按鈕，所以只驗證了擋 Run 的邏輯，沒有驗證使用者按下去看到什麼。

使用者的要求：「我必須要想一個辦法或機制讓agent能自己做e2e測試，我只要負責品味設計就好，而不是行為測試」。

## 現況

- measure-gui 的 remote RPC 與 MCP 操作 Controller，也就是程式的指令介面，同樣繞過元件。它可以截圖，但不能點擊元件。
- Repo 沒有 pytest-qt。`tests/gui/_user_input.py` 已能對單一元件送鍵盤與滑鼠事件。`tests/gui/app/measure/_app_launch.py` 已能啟動真正的 measure-gui 行為，包含視窗、Controller 與 remote adapter。
- 直接操作元件的既有測試只有少數幾個檔案。

## 考慮過的選項

| 選項 | 內容 | 成本 | 確定性 |
| --- | --- | --- | --- |
| A：元件驅動情境（採用） | pytest 內 offscreen Qt。Driver 依畫面文字或元件名稱找元件，送真實事件，讀使用者看得到的狀態，每步截圖 | Driver 約 200–300 行，第一批框架情境約 300–400 行，流程規則約 10 行 | 確定，可進 CI |
| B：remote／MCP 新增 UI 操作 RPC | Agent 在使用者桌面的 live GUI 裡點元件、打字、讀畫面文字，代替使用者走查 | 遠端介面要加一組能力，還要限制在模擬環境並做安全審查 | 取決於 live 環境 |
| C：OS 層自動化 | xdotool 或 AT-SPI 驅動視窗，加上截圖給 vision 模型判讀 | 產品碼不用改 | 脆弱、慢、不穩定 |
| 只加流程規則 | 不做共用 driver，每張票用既有 input helper 臨時寫 | 幾乎為零 | 每張票重寫找元件與讀畫面，容易再次繞過按鈕 |

## 被否決的選項與理由

- **B**：遠端介面多出「點任何按鈕」的能力，可能誤觸真實硬體，必須限制在模擬環境並另做安全審查，成本比 A 高。之後若需要探索式的 live 代走，再重新評估。
- **C**：脆弱、慢、結果不穩定，不適合作為驗收條件。
- **只加流程規則**：成本最低，但沒有共用的找元件與讀畫面能力，這次「繞過按鈕」的錯誤很容易重演。

## 留下的問題

- Driver 找元件時要靠畫面文字還是 objectName。若需要替產品元件補 objectName 或 accessible name，由實作 task 提出。
- 截圖判讀目前由 agent 自己看圖。是否需要固定的檢查清單（例如「每個被擋的操作都有可見原因」），留待第一批情境後再定。
- B 的 live 代走是否值得做，等 A 跑過幾個 UI task 後再評估。
