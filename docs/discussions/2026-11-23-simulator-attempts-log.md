# 模擬器優化嘗試記在哪裡

## 結論

使用者選擇一個目錄、一份索引，每次嘗試各寫一檔。第一批也補登已知的過去嘗試。收錄規則與單檔模板在[模擬器優化嘗試索引](../simulator-attempts/INDEX.md#收錄規則)。已有討論的嘗試連到原文，不重寫比較與量測表。

## 問題

採用過的做法散在討論和模組 README。沒採用的嘗試有時只留在未入庫的工作檔。下次想加快模擬器時，從現行程式看不出哪些做法已試過、當時用的版本，以及為什麼沒有保留。

使用者提出：「還有，我認為優化器模塊的readme或相關文檔，應該有個檔案專門記錄嘗試過哪些優化手段，在哪個commit做的，是否採用，核心思路為何，這有幾個好處，分別是避免重蹈覆轍，以及提供後續優化的靈感」

隨後他確認對象與版面：「我不是很喜歡丟在一個檔裡，這樣行數會爆炸，我傾向一個目錄與一份INDEX，每次嘗試一個檔案，還有我指的是 模擬器 而不是cz_optimize」

## 考慮過的選項與比較

- 單一大檔可以從頭讀完，但每新增一個嘗試，正文與索引都會增長。
- 在[討論索引](INDEX.md)加欄位，可沿用既有討論的日期和連結。沒有討論檔的試作仍需要另外有地方放。
- 一個目錄加索引可先按主題查找，再開單檔看結果和驗證範圍。有原文的只保留入口，沒有原文的在單檔交代依據。
- 只建結構可供下一次嘗試使用，但不處理當時已經分散的舊證據。

## 被否決的選項與理由

使用者否決單一大檔，因為行數會不斷增加。擴寫討論索引也未採用，因為沒有討論檔的試作仍會漏掉。對只建結構或一併整理舊嘗試的選擇，使用者答「建目錄並補登」。

## 留下的問題

一些歷史量測沒留下可核對的 commit。遇到這類資料，索引說明證據缺口，不把後續落地版本當作原量測版本。此次沒有重跑模擬，也不收 `cz_optimize` 優化器的嘗試。
