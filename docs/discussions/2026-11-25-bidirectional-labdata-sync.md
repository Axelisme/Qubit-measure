# 以逐檔基準交接 Labdata

## 結論

兩台電腦選同一個 prefix 和雲端根，各自把 checkout 的 `result/` 和 `Database/` 連到實體 Labdata。`push`、`pull` 和 `sync` 共用這對路徑。仍保留單向推拉，讓操作者能明確選擇覆寫方向。

雙向同步在動資料前列出全份計畫。沒有基準時，依檔案的修改時間取較新的一份。同時間需要內容證據。有基準後，依兩端各自相對上次確認一致時的變化選方向。無法裁定或遇到單邊刪除時，不開始該 prefix 的傳輸。操作方式寫在[資料同步指南](../data-sync.md#兩台電腦輪流接手)，驗證與失敗語意寫在[同步模組契約](../../lib/zcu_tools/utils/data_sync/README.md#雙向計畫)。

## 問題

[先前的同構資料樹](2026-11-25-multi-machine-data-sync.md)讓量測機推到雲端，彙整機按來源拉到實體資料根。當時的 push 仍從 checkout 讀資料，pull 則寫到外來資料根。兩台電腦要輪流在同一個資料集量測、分析和存檔時，推拉路徑並不對稱。單向的時間比較也分不出誰在上次同步後修改了同名檔案。

## 比較過的選項

- **每次用時間選版本。** 第一次沒有可用基準，這個做法可以直接啟動。但之後仍只看兩端目前的時間，時鐘偏差或手動保留時間都可能讓未修改的一端蓋掉改過的版本。
- **保存各端的時間與大小。** 在證實兩端內容相同後才記下兩份 metadata。下一次能辨識單邊修改和同時修改，不用讓兩端的時鐘一致。它仍不能偵測保留原時間與大小的改寫。基準留在 Labdata，不加雲端控制檔。
- **單邊刪除時暫停，兩端皆已刪除時清除基準。** 不讓刪除自動碰另一端。2026-11-25，使用者指出保留兩端已刪除的紀錄會累積暫存檔和搬移前的位置：「那我就把它删掉……结果残留了一大堆记录，越累积越多，这不好啊。」因此只在兩端都不存在且同步成功後清除紀錄，同名重建可當成新檔。
- **按方向批量搬運。** 計畫給出確切路徑，再由 rclone 平行複製。已決定方向的檔案不因事前缺 MD5 而阻止搬運，但驗後缺證據就不能算同步完成。使用者說：「很多场景跟防御性设计我不确定用不用得到。用不到那就是浪费维护的心力」。已傳檔案不回滾，讓操作者看見驗證未通過的項目，只更新能確認的基準。

## 被否決的其他選項

- **雙向強制、合併內容或傳播刪除。** 雙向強制無法說明要留哪一份；YAML、HDF5 和 ledger 也沒有共用的安全合併規則。保留明確指定方向的單向推拉，不讓 `sync` 代替人工決定。
- **逐檔啟動程序或先打包整棵資料。** 逐檔啟動 rclone 不能共用該方向的批次；打包讓雲端失去可逐檔瀏覽的同構布局。兩者都不是為了做計畫所必需的。

## 留下的問題

本方案假設兩台電腦輪流寫入，不鎖住本機、雲端或 GUI。衝突須人工處理。實際可取得的雜湊由端點提供。驗證失敗能阻止基準進到未證實的狀態，但不會還原已複製的檔案。

## 依據

保留舊方案的同構 project root 與任意相對 prefix，替換僅從單一 checkout 上傳、另在彙整機存本地副本的傳輸路徑。遵循 [ADR-0072](../adr/0072-module-boundaries.md#分層)：CLI 仍注入 checkout，工具不解讀量測資料，也不改 GUI 的資料根或依賴方向。固定版 rclone 提供 NUL 分隔的路徑清單，讓批次路徑不當成 glob 或行文字解析。原始工作紀錄未入庫。
